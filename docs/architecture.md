# Architecture

One actor, one file of rules, everything else is plumbing. About 1,500 lines of plain ESM with no dependencies.

```
bin/gallivant.mjs        CLI: parse args, build the context, call one command
lib/context.mjs          wires the real dependencies once (config, state, gh, git, notify, log, runner)

lib/tick.mjs             the state machine. Settle runs, fetch, terminal states, events, dispatch, ready, silence.
lib/events.mjs           pure rules: what counts as an event, trust, reviewer verdict, green checks, round counting
lib/prompt.mjs           start, register and fix prompts; quoting and caps
lib/harness.mjs          adapters: argv per harness and mode, session id extraction, outcome parsing, sign-in probe
lib/block.mjs            the PR body block: render, strict parse
lib/prd.mjs              the contract: frontmatter, sections, rules, criteria, Verify commands, and the comparison of
                         the daemon's snapshot with the operator's own copy. Takes a Request, not a file
lib/hash.mjs             one fingerprint spelling: twelve hex characters of a sha1, for the receipt and the contract
lib/sources/             one adapter per source of a brief, and the registry that picks one. Only the PRD file today
lib/deliverable.mjs      the completion gate: criteria from the PRD, the receipt, the policy's rules and deny codes

lib/gh.mjs               the only GitHub access, through the gh CLI; login normalisation; markers and labels
lib/git.mjs              per-PRD checkouts (partial clones), the base-branch merge, run environment
lib/run.mjs              detached runs; liveness checks that the pid still runs the harness, adapted from command-center
lib/state.mjs            the registry: atomic writes under a lock file, pure ids, handle resolution
lib/config.mjs           defaults, validation, path expansion
lib/notify.mjs           ntfy messages and the throttled error class
lib/probe.mjs            health checks shared by doctor, start and the daemon
lib/aport.mjs            what APort's installer leaves on disk: the mode file and the audit log, one parser each
lib/log.mjs, fs.mjs, time.mjs

lib/tracker/stream.mjs   the SSE log tail: bounded first read, resume by last-event-id, follows the log file
lib/tracker/runs.mjs     the index over ~/.gallivant/runs, and the id checks every route goes through
lib/tracker/pages.mjs    the pages: escaping, the sidebar and its groups, the run detail pane, the CSP
lib/tracker/assets.mjs   templates/tracker/{tracker.css,tracker.js}, read once, plus the ?theme value

lib/commands/            start, register, up (daemon + reconcile), status, why, doctor, serve
test/                    node --test; helpers.mjs holds the fakes
templates/               passport, Claude sandbox settings, PRD, tracker/{tracker.css,tracker.js}
```

## Design rules

Harness implementation and demonstrated support are separate. The [live support matrix](audit/harness-live-validation.md)
records installed versions, provider/model combinations, permission boundaries, budget controls and blocked phases.
Claude/Codex have existing production evidence; Gemini, OpenCode and Goose currently have blocked or failed coding attempts,
not successful start/resume proof. Provider subscription eligibility is independent of the harness adapter.

Repeat with `npm run test:live-harnesses -- --live` after the recorded operator remedies. The opt-in
`test/live-harnesses.mjs` is outside `test/*.test.mjs`; it uses the existing `buildRun`, `runEnv`, `makeRunner`,
version probe and outcome/session readers. Test-local native model overrides do not add per-task model selection
to Gallivant. `test/live-support.mjs` verifies model evidence, adapter identity, actual test tool execution, files,
behavior, commits, upstream and remote HEAD. Calls are sequential, at most 180 seconds per turn and 30 minutes
per suite, with one start/resume pair and at most one justified targeted retry per combination. Refusals stop
the affected phase; they are never converted into permission overrides. Ordinary command stderr such as
`Permission denied`, `Operation not permitted` or `PermissionDenied` is retained for investigation without
triggering an approval stop. Sandbox classification requires workspace/sandbox context; explicit permission
requests/rejections and guardrail decisions still stop the turn. Raw streams and exports stay private.
Recognized unsuccessful native outcomes (such as an aborted OpenCode step) are recorded as
`native-failure`, not adapter defects. The retry gate checks both saved outcome metadata and the
current parser's reading of the saved stream; a source change cannot qualify these failures for retry.
Goose's textual provider-error prefix must start an assistant message/content block. The adapter reads
across streamed chunks from those boundaries, preserving native failures after earlier output without
treating error examples embedded in prose or code fences as failed turns. Typed native errors remain failures.
Named Meta/xAI/Alibaba cases use Goose's native saved providers and OpenCode's separate Console BYOK
providers; they do not establish Zen/Go subscription access. Exact batch commands and blocked results are
in the audit. DeepSeek is excluded from new calls and Tencent remains deferred.

Every OpenCode turn pins `--model` to the case's recorded provider/model, including the existing-default
case. An unknown, incomplete or routing-alias default blocks before fixture creation or launch. Changing
native defaults afterward cannot change that pinned argument, and exported model evidence must match the
recorded selection on both turns. Named Console providers keep their exact selectors.
Goose likewise requires known provider and model selectors before fixture creation or turn reservation;
both are always passed explicitly. Missing or unparseable settings block without falling back to its
mutable default. Native environment/settings and the named Meta/xAI/Alibaba selectors remain supported.

Disposable turns clear inherited Git/GitHub/SSH, credential-manager and editor askpass variables, then
restore `runEnv`'s Git identity and isolated config with terminal credential prompts disabled. Git accepts only
file transport and its SSH command refuses execution, preventing default SSH identity fallback while keeping
provider `HOME` intact. Child-environment controls do not replace native sandboxing. Short-lived callers use the
runner's `waitForKill` after requesting a stop so the process-group fallback runs before exit; the live suite
also waits before metadata export. Signal/watchdog callbacks defer checkpoints to the main async path;
failed ledger or runner metadata writes still reference and await the kill fallback before surfacing
the error. A pending kill owns its exit record, so an early leader exit cannot cause another metadata
write failure before descendants are stopped. An append can
reuse a version-blocked case after upgrade only if it has no turn, retry reservation or fixture, within the
original deadline and with the recorded provider/model unchanged.

Runner startup is awaited by initial dispatch, resume/fix dispatch, and the live suite. The runner
owns its freshly spawned PID until it returns a recorded job; a failed `job.json` or `latest-run`
write terminates that process group and awaits the existing kill fallback before rejecting. This
cleanup uses the in-memory job even if disk bookkeeping is missing or truncated. Startup-error
callbacks cannot repeat failed writes, and the parent's log descriptor closes on every startup path.
Live turn reservations remain spent when startup bookkeeping fails.

The shared runner pins child `PWD` to its requested working directory. OpenCode 1.18.31 prefers that
environment variable for its tool directory, so changing `spawn.cwd` alone is insufficient. The live suite
checks native session directory evidence and stops on a mismatch; start fixtures must have no prewritten
files or remote commits. See the audit's directory incident and recovery record before repeating a failed case.
An eligible start retry gets a distinct pristine checkout/remote while retaining the original fixture and
turn evidence; resume retries still require the last passed checkout and remote state. Retry and time limits
are unchanged, and no historical failure or exhausted retry is relabeled by these fixes.

Every turn reserves its case, fixture, source, invocation and running record in the atomic ledger before
launch, including first starts and resumes. The reservation points to the private runner directory even if
a crash prevents recording the job ID. A running reservation cannot be appended or retried as an unspent
case; inspect its private runner evidence and resolve any surviving process before scheduling further work.
The final deadline check includes reservation I/O and releases the reservation only when no launch occurred.

A passing disposable test would still not establish GitHub review/completion behavior. Full support requires
an authorized PRD through `ready`/`start`, PR creation, review/CI feedback, a same-session pushed fix and the
completion gate. Keep that lifecycle evidence separate from session fixtures and disposable local Git tests.

- **The tick is the only writer.** Nothing changes state in exit handlers, timers or callbacks. A finished run is noticed on the next tick by asking the OS whether the pid is alive and reading the log. That is what makes a daemon restart mid-run safe.
- **Rules are pure.** `events.mjs` takes the raw shapes `gh` returns and produces events. Every rule in the PRD has a unit test with no network.
- **One gate, and the brief is a Request.** `check()` takes a source-neutral Request, `{ id, repo, title, body, harness, status, source: { kind, url, author }, raw }`, plus the parsed fields the rules read. A source under `lib/sources/` reads whatever the operator typed and produces one; today the only source is a PRD file, and its Request is exactly what `parsePrd` always returned. Two things follow. A rule that depends on where the brief lives rather than on what it says carries its own scope as data (`kinds: ["prd"]`: `path`, and `sources` because it resolves the files a brief carries against the repository root that path gives it), so a source without a path is not failed for a rule it cannot satisfy. And `repo` is a field the source fills in, not something a command derives: `start` reads `request.repo` and never calls `git.toplevel` itself. Adding a source is an adapter plus somewhere to record its verdict, never a second gate.
- **Dependencies are injected.** `makeTick` receives `gh`, `git`, `runnerFor`, `notify`, `clock`. The test suite builds fakes in `test/helpers.mjs`; the CLI builds real ones in `context.mjs`.
- **Per-harness knowledge lives with the adapter.** `harness.mjs` owns each CLI's argv, its session id shape (`isSession`), its sign-in check and the command that fixes a failed one (`signIn.fix`). `HARNESSES` in `config.mjs` is the keys of that object. A rule about a harness written anywhere else goes stale the moment an adapter is added: a UUID regex in `block.mjs` was refusing goose's and opencode's real session ids, and `doctor` was telling three harnesses to run `codex login`. Everything that can put a session id into argv goes through `isSession`, the block and `register --session` alike, because `assertSafeArgv` matches flag spellings and cannot judge a value in a position it does not expect.
- **GitHub is the source of truth for identity; the registry for counters.** Both can be rebuilt: identity from the PR block, counters from the daemon's own marked comments (every round posts one, a reset posts one).
- **Four cursors, one meaning each, and none of them goes backwards.** Monotonicity is enforced in `advanceCursor`, not asked of each caller: three callers pass a boundary from a different source (the newest event dispatched, the head commit's committer date, a local clock reading) and a candidate before the cursor is refused outright, keys and all. `since`: events at or after it are new. `fixed_sha`: the head the loop last acted on, both the head when the last run started, so a push by a fix run is the head moving, and the head a ready entry was judged on, so a push after that reopens it. `checks_sha`: the head whose failing checks were already dispatched. `receipt_hash`: the completion receipt when the last run started. `since` is inclusive because GitHub stamps events to the second, so two that arrive in the same second share a timestamp; `dispatched` rides alongside it with the ids already handled at exactly that instant, and is cleared the moment the cursor moves to another second.
- **One run per entry is the lock.** A run root per entry means a second dispatch for the same PR is refused by the runner while the first is alive, and entries never block each other.
- **Every wait is bounded, and every stop has a reason.** Five steps in the tick decline rather than proceed when one GitHub write will not land, because proceeding would leave a worse state than waiting: the ready-label removal before a dispatch, the same removal before a moved head is judged, the identity block write a start run must land before it can leave `running`, the ready-label write that makes a judged PR say a human may merge it, and the round comment a settled round owes the PR. The fifth declines the rest of its tick rather than the round it announces, because the round is a push that already happened; the other four decline work that has not happened yet. All five are right to wait and none of them may wait forever, so `entry.retry` counts the CONSECUTIVE failures of one named write and the entry stops with `stuck` at five, naming the write and what GitHub said. The count resets the moment that write lands, so an entry whose GitHub came back is never stopped for the ticks it spent failing, and a different write failing starts its own count rather than adding to the old one. One mechanism for all five, and for any sixth: the recurring defect in this codebase is the same invariant enforced on one path and not its sibling, so a second counter would be the next finding. What makes a step belong here is not the write but the shape, so the list is expected to grow: the step declines, the entry stays in a state the next tick re-enters, and nothing else about the entry has changed. Two of the five were added a round after the first three, both found by enumerating the writes rather than by a failure report. Five is a constant with a comment in `tick.mjs` rather than a config key: the only question it answers is "transient or permanent", ten minutes at the default `poll_seconds` outlasts a rate-limit window and falls far short of a revoked token, and `max_iterations` is the wrong knob because it counts rounds that cost money where these cost one API call.
- **The snapshot is authoritative against the session and disputable by the operator, and those are two different rules.** `start` copies the brief into `~/.gallivant/prds/`, and the files it names in `sources` into `~/.gallivant/prds/<id>.sources/`, and the gate reads only those, which is what stops a session widening its own acceptance criteria. It does not stop the operator editing their own copy, and until the comparison existed nothing noticed: a run finished against criteria nobody was asking for, and the PR arrived satisfying a document that had changed. So the two files are compared, in the contract's own terms and no others (`criteriaFromPrd`, `verifyCommands`, `harness`, `context_paths`, `sources`), and the verdict decides the action. A brief edited outside those five is followed silently, because an entry stopped for a reworded Problem section is an entry whose operator learns to ignore this. A brief whose contract moved stops with `prd-changed` and the specific difference, because ADDED (valid but incomplete) and REWRITTEN (invalidated) are the same event in two files of text and guessing wrong is expensive in both directions. A brief that no longer passes the contract is `prd-illegal` and never reaches the snapshot, since one `start` would have refused is worse behind the gate than one merely out of date. A brief deleted is `prd-gone`. An entry with no recorded checkout, which is every entry `register` and `reconcile` build, compares to `unknown` and carries on, so recovery from GitHub is not made useless by a tree it was never told about.

  **The verdict is a fingerprint's, and the diff only explains it.** `sameContract` compares `prdFingerprint` over the whole ordered contract; `contractDiff` produces the lines a person reads. Keeping those two jobs apart is the fix for a family of false negative, not tidiness. A diff has to group and set-subtract to be readable, and set arithmetic loses information: a second `- \`npm test\`` in the Verify section leaves every element of both lists present in the other, so the diff is empty while the commands the session must run green have changed. Reordering two criteria is the same shape, and it got its own targeted fix (the criteria are compared as `id: description` pairs, because `criteriaFromPrd` numbers them by position and the receipt on the open pull request attests those numbers, so a swap leaves both ids meaning the other thing and the receipt attesting each criterion with the other's evidence). A targeted fix per shape is a bug per shape nobody has thought of yet, so the verdict asks the one question a hash answers exactly, and a `changed` verdict whose diff came back empty says so in as many words rather than stopping an entry with nothing to show for it.

  One reason this comparison had to fix `parseFrontmatter`'s line endings on the way past: the regex matched `\n` only, so a CRLF copy of a brief parsed as having no frontmatter at all and fell back to the default harness. That was survivable while `ready` was the only reader, with an operator in front of it. It stops being survivable when the brief is compared against a running entry, where a `.gitattributes` change reads as the harness changing and stops a healthy run blaming the wrong thing.

  **Where it runs, and why the daemon reads the operator's tree at all.** Two halves, one implementation in `prd.mjs`. The tick is the only actor that changes state, so a comparison that lived only in `status` and `why` would be a warning while the daemon finished the work anyway. But it does not run every tick on every entry: `entry.checkout` is a path on the operator's machine, and a stat and a parse per entry per poll for something that changes a handful of times per run buys nothing, while an unmounted volume would read as `gone` and stop healthy entries. So the daemon compares at the one point the contract is USED to certify something, immediately before the completion gate, and everything earlier (a fix round for a review, a round counted for a push) proceeds against the brief the session holds, because a dispatch is not a claim that the brief is satisfied. `status`, `why` and `resume` compare on demand, in the operator's own session where reading their checkout is unremarkable and where they are asking the question. **While a `prd-changed` stop is unresolved the gate judges neither brief**: the snapshot certifies one the operator abandoned, the edited copy certifies criteria the session never saw and never attested, and there is no third brief.

  **A re-snapshot is an explicit act with an audit trail.** `ensurePrdSnapshot` is still the one writer and still refuses to overwrite; what changed is that the refusal is no longer absolute, because a brief the operator has deliberately edited can only become the brief the gate judges by replacing the snapshot. `resolvePrdSnapshot` is the only path to that, reached only through `gallivant resume --resnapshot`, and it warns with the file, who asked and every difference, in the same spirit as the existing line that says the session could have edited the copy it took. `retakePrdSnapshot` shares the writes for the silent case so a third caller cannot invent its own way to put a file in `prds/`. And the fingerprint is `shortHash` in `lib/hash.mjs`, which `receiptHash` now calls too: one spelling of "twelve hex characters of a sha1" rather than two that agree today.
- **Adapters own the flags.** Config holds binaries and paths only. A CLI upgrade changes `harness.mjs`, and `assertSafeArgv` refuses any `--dangerously-*` flag no matter who adds it.
- **Reuse over build.** `gh` for the API, the harness's own resume and no-prompt flags, APort's own installers, ntfy's email header, command-center's runner layout so its log viewer can read a Gallivant run.
- **One value, resolved in one place.** The base branch is read by three things that must agree: the branch the checkout is cut from, the `gh pr create --base` the session is told to run, and the branch merged in before each round. `resolveBase` in `config.mjs` is the only thing that decides it, from the flag, then the repository's entry in `repos`, then the repository's default branch. Three callers working it out for themselves would agree by luck, and the failure when they stopped agreeing would be a pull request opened against a branch nobody chose.

## The tick, step by step

For each registry entry that is not `done`:

1. **Settle.** Only the run this entry dispatched (`last.run`) is looked at, ownership first: a live run left behind by a reset or a recovery is ignored rather than waited on and then killed and blamed on the entry. If that run is alive and past `run_timeout_minutes`, kill it and stop with `timeout`. If a run ended and is not yet recorded: for a `running` entry, find the PR on the branch, write the block, enter `pr-open` with the event cursor and the reviewer clock at the PR's creation time, so a review that landed during the start run is seen; or stop with `no-pr`. The block write is a precondition of leaving `running`, not a best-effort extra: it is what recovery rebuilds the entry from once `state.json` is gone, so a failure keeps the entry in `running` with `last.exit` still unrecorded, which is the state the next tick re-enters and retries from. The session is saved on the way out so a retry never mints a second one, and the retry is counted: five consecutive failures of that write stop the entry with `stuck` rather than holding an open PR unwatched in silence, and the stop records the PR number so the message and `gallivant why` can link it. For a `pr-open` entry, the head moving or the receipt changing is a round: bump the iteration, move the cursor to the push, record the run's exit, and note that the round comment is owed. Then post it, in step 4. Otherwise stop with `no-push` or `harness-error`.

   The order there is the point. What happened is a push: a harness run spent money and moved the branch on GitHub, and nothing that fails afterwards can un-spend it. The comment is the announcement of that fact, and `max_iterations` is the only bound on what one PR may spend, so a counter that waits for the announcement is a bound that can be exceeded. The comment used to be the precondition of counting, which meant a refused comment left the push on GitHub, the fix in the branch and the iteration unchanged. So the local write goes first and the GitHub write goes last, which is the same rule the identity block write follows from the other side: order a pair so the irreversible half is last, and here the irreversible half already happened before the settle ran, which leaves the replayable half to a later tick.
2. **Fetch.** `gh pr view --json` for state, head, checks, issue comments, labels and body; REST for reviews and inline comments since the cursor, asked for from a second before it so the boundary second comes back whatever GitHub's filter does with it.
3. **Terminal.** Merged or closed is `done`. Conflicting is `needs-human`. A `needs-human` entry is checked for nothing else, except the two labels a stop owes the PR, which are retried here until they land. The base branch is then taken from the PR's own `baseRefName` rather than from anything remembered, because GitHub is the only authority on where a pull request is aimed: it is how an entry written before the field existed gets one, and how a PR someone retargeted from `main` to `staging` starts being merged against the branch it now targets.
4. **The round comment.** Owed by any round the settle counted and could not announce, posted here on the tick that counted it and again on every later tick until it lands. Idempotent against its marker, so a comment that reached GitHub under a failed response is not posted twice. It is a count on the same `entry.retry` as the four declining writes, for the same reason: a token that can push but cannot comment never recovers, and the markers on the PR are what a recovery rebuilds the iteration from, so an entry whose rounds are invisible to a recovery must not be left running in silence. What it declines is the rest of this tick rather than the round, because the comment is also the re-review request: an entry that owes one has asked the reviewer nothing, so its silence must not be judged and a second round must not be charged before the first is announced.
5. **Events.** The rules in `events.mjs`. Failing checks count against `checks_sha`, so red CI on a head the loop itself pushed is dispatched once; if it stays red on that head after the fix, the entry stops with `checks-red`.
6. **Dispatch.** Past the cap, stop with `iterations`. Otherwise recreate the checkout if it is gone, merge the base branch into the work branch, build the fix prompt, resume the session (or start one for a registered PR), move the cursor to the newest event and record the ids dispatched at that instant, record the run.

   The merge is where a round of work starts from the current base rather than from wherever the base was when the branch was cut, and it is a merge rather than a rebase for three reasons that all live in this codebase. A rebase of a pushed branch can only move with a force-push, which the rules every session is given forbid. `reviewerVerdict` clears a head only when the commit the reviewer named is that head, so a rewrite makes every prior clearance describe a commit that no longer exists, and the reviewer's inline comments are anchored to those same commits. And step 7 reads a head the loop did not put there as a person's push, so a daemon force-push would look to the daemon itself like a stranger pushing. A merge moves the head forward, keeps every reviewed commit an ancestor, and needs no `--force`. An outstanding review therefore does not hold it up, which is the point: a rebase would have had to wait for the review, and that is a deadlock where the reviewer waits for a fix and the fix waits for the reviewer. The merge commit stays local until the session pushes, so nothing on GitHub moves, the reviewer clock is not reset and the round is still counted from the session's own push. It is recorded the moment it succeeds rather than by the save at the end of this step, because four things after it can return early and a merge nobody recorded is a change to a checkout with nothing to explain it. A conflict is aborted and the entry stops with `base-conflict` naming the base, because a half-merged checkout handed to a session as if it were clean is the worst thing this step could leave, and a conflict does not resolve on its own so retrying every tick would loop forever. Four things that would refuse identically on every poll stop the entry instead of looping: a checkout that cannot be recreated (`no-worktree`, with the cause as the event), a harness that refuses the configured `context_paths` (`context-paths`), no GitHub credential (`no-credential`) and no git identity on the machine (`no-identity`, whose event is the two `git config --global` commands that fix it). None of them resolves on its own, and the entry would otherwise redispatch the same feedback every poll with nothing notified. One invariant orders the rest of this step: **a spawned run must be recorded before anything else can fail.** Everything that can throw, the checkout and the ready-label removal included, happens before the spawn, and the registry write that owns the run comes immediately after it with no `await` in between. A process the registry does not know about is the worst state the dispatch can leave, because the settle step reads it as an unrelated leftover and the feedback that caused it is still new, so the same feedback spawns a second fixer when the first one exits. The label removal is the one write that can therefore hold a dispatch back, and holding it back is bounded: five consecutive failures stop the entry with `stuck`. `gh.removeLabel` throws by default and swallows only gh's own "label not found", which is what makes that bound reachable at all: the lenient behaviour was once the default, one of the two callers omitted the flag, and a GitHub that refused the write resolved as though the label had merely been absent.
7. **Ready.** First, a head nobody told the loop about. Both watching states go through the same check, in one place: `fixed_sha` follows the head, the reviewer clock resets to the push and the nudge becomes available again, because the reviewer has not seen this commit. A `ready` entry also leaves ready with the label off, since its verdict, its green checks and its accepted receipt all describe a commit that is not the head any more. Handling it for `ready` alone used to leave a `pr-open` entry judging the new head with the old head's age, so the same tick that noticed the push could stop it as `reviewer-silent` on a wait that expired before the commit existed, and the nudge already spent on the old head was never reissued. Then, for a `pr-open` entry: no events, no run, not a draft, every check green (none counts as green), reviewer clear or absent. Then the brief, compared with the operator's own copy: this is the only place the daemon reads their working tree, and it is here because this is where the contract is about to be used to certify something. A contract that moved stops the entry with `prd-changed` and the difference named, before the gate runs and without setting `gate_skipped`, which describes the other thing entirely (a PR that reached READY with the gate unrun, where this entry is not reaching ready at all). An edit outside the contract re-takes the snapshot, notifies nobody and carries on. Then the completion gate (`deliverable.mjs`): the PR body's receipt must attest every acceptance criterion of the PRD with evidence; a deny starts a receipt round. A receipt whose shape is wrong is one of those denies, not an exception. The output scan needs the whole diff, so a diff that cannot be read or reaches the 16 MiB scan cap is no decision at all. Large hosted payloads are sent in overlapping pieces within the API request limit, with full criteria and attestations on each; every piece must allow. Unreadable diffs and unavailable evaluators use the same bounded `entry.retry` mechanism as writes, with the cause visible in `status` and `why`; five consecutive failures stop as `needs-human`, without a fixer run or iteration. The label goes on before the registry says ready, so a label write that fails leaves the entry in `pr-open` to be retried rather than a ready PR carrying no label, and those retries are counted on the same `entry.retry` as every other declining write: a token that cannot write labels at all used to repeat the readiness judgement, the completion gate included, on every poll forever, while `status` said the entry was waiting on a reviewer who had already answered. Only then notify, once.
8. **Silence.** Reviewer configured and quiet since the last request: nudge once after `rereview_minutes`, stop with `reviewer-silent` after `stall_hours`. A draft PR that meets every other ready condition stops with `draft` instead, since it falls through the ready branch and through all three of these and only a person can take it out of draft.

The reviewer clock (`rereview.at`) is when the reviewer was last asked about the current head, and all three of those timers measure from it. Its best available value is the head commit's committer date, which is when the commit was made and not when it arrived on the branch, so it is floored at `rereview_minutes` ago: a commit made on Monday and pushed on Thursday must not stop the PR for a silence the reviewer was never given a chance to break. The rule is `reviewerClock` in `events.mjs`, pure and in one place because the tick is not its only writer: `reconcile` sets the same field on a recovered entry and goes through the same function, so a PR whose last round comment is older than `stall_hours` is not stopped `reviewer-silent` on the first tick after a crash recovery for silence that accrued while no daemon was running to ask.

## The tracker

`gallivant serve` is a read-only window onto the same files the CLI reads. It has no route that starts, kills or resets anything, only GET is routed, and nothing under `lib/tracker/` writes to disk, so the tick stays the only writer. Seven rules hold it together:

- **One model, three renderings.** The dashboard, the sidebar and `/api/status` all come from `model(ctx)` in `status.mjs`, the same function the text view uses. A group that appears in one appears in all of them.
- **An id is validated against the registry, not by pattern.** Entry ids contain slashes, so a query string is accepted only when `state.get(id)` returns an entry; the path is then rebuilt from `idSlug`. Run ids go through `run.mjs`'s `[A-Za-z0-9_-]` check. Nothing from a URL is ever joined to a path directly.
- **The log is followed as a file.** The stream watches `job.log` with `fs.watch` and a one-second timer underneath, not the child's pipes, so a browser attached after a daemon restart still sees a run this process never spawned. It sends the last 400 lines on connect with a `skipped` count, carries an `id:` on every frame, and honours `last-event-id`, so a reconnect resumes rather than replaying. `res.setTimeout(0)` on the response, the request and the socket keeps Node's five-minute `requestTimeout` from cutting a long fix round. This is ported from command-center, where each of those was a bug first.
- **The log renderer is command-center's, ported.** `renderLine` and its parse come from that project's `public/logline.js` unchanged apart from an inlined escaper, because a Gallivant run log is harness output and that is the shape the file was written for: an indented `Tool: argument` line, or prose, with URLs inside either. Tool calls get their own column and colour, the closing line is coloured by outcome. Text is escaped before anything is built from it, so only markup the renderer itself wrote is ever inserted. A fix to those regexes belongs in both copies.
- **Everything interpolated is escaped, and the page runs no inline script.** PR titles, branch names, reasons, run names and log lines come from GitHub or an agent. The CSP is `default-src 'none'; script-src 'self'; style-src 'self'`, and the stylesheet and script are files under `templates/tracker/` served on their own routes, so there is no nonce to thread through a response and no hash to keep in step. Log lines reach the DOM through `textContent`.
- **Grouping is a link, not state.** The sidebar groups by entry state or by harness, chosen with `?by=`, so a grouped view is something you can bookmark or frame and there is nothing to keep in sync between the server and the page. Two options and a small switch, not a grouping engine. Collapsed state is the one thing the page keeps, in `localStorage` per view; a filter ignores it and shows every match expanded, which is the detail that makes a search feel right.
- **The palette can be forced from outside.** Every colour, font and spacing value is a `--gv-*` custom property with a default. A same-origin parent can override them; a cross-origin parent cannot touch this document at all, and CSS custom properties do not change that, so `?theme=dark|light` is the mechanism for that case. It stamps `data-theme` on the root element, because `prefers-color-scheme` inside an iframe follows the browser and not the page that framed it.

- **The router is separable from the server.** `handle(ctx, req, res, { base })` is the whole of the routing and `mount(ctx, { base })` wraps it as `{ owns, handle }` for a host server to delegate a prefix to, so the tracker can run standalone on its own port or inside a server somebody else starts. Every URL the pages emit is built from the mount path rather than from the root, and the script reads that path from `<body data-base>` since it is one static file that cannot be told at build time where it lives. A mounted tracker inherits the host's bind address and auth, which is the host's responsibility and not something this module can enforce.

Standalone it binds `127.0.0.1` with no auth: the same trust boundary as the CLI, since anything that can reach it can already read `~/.gallivant`.

## Adding a harness

Add an adapter to `lib/harness.mjs` with `start`, `resume`, `env`, `sessionFrom`, `outcome`, `signIn`, `version` and `attach`, add its name to `HARNESSES` in `config.mjs`, and add its minimum version. OpenCode is next: `opencode run --format json --auto`, resume with `-s <id>`.

## Adding a reviewer

No code. Set `reviewer.login`, `reviewer.rereview_comment` and `reviewer.blocking_pattern` in config.
